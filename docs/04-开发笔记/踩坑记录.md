# 踩坑记录

## 1. Windows 下 `cargo run` 和 `cargo test` 可能触发 `os error 5`

- 现象：在当前机器上，`cargo run`、`cargo build`，以及并发的 `cargo test` / `cargo run` 很容易在 `target` 或 `incremental` 路径上报“拒绝访问”。
- 影响：逻辑测试可能通过，但实时二进制刷新和 live smoke 验证不稳定。
- 当前处理：优先用 `cargo test` 和 `scripts/verify.ps1` 做逻辑验证，把 live binary 刷新问题单独追踪在 `[[ISSUES_TODO]]`。

## 2. 自索引开发仓库会带来检索噪音

- 现象：如果直接把当前开发仓库全部 ingest，查询时会命中测试代码、README、计划文档、开发笔记。
- 影响：top hits 质量下降，普通代码查询更容易被非实现内容污染。
- 当前处理：通过 `IngestPolicy`、source weighting、fact-first presentation 和 source hygiene 降噪。

## 3. Obsidian CLI 的调用方式和普通命令不完全一样

- 现象：当前环境里直接敲 `obsidian help` 不稳定，但通过显式路径 `D:\Obsidian\Obsidian.exe` 可以进入 CLI。
- 影响：自动化脚本里不能假设 `obsidian` 已经像普通 PATH 命令那样稳定可调。
- 当前处理：文档资产继续按 Obsidian 规范维护，自动化调用优先使用显式可执行路径。

## 4. `defuddle` 当前环境不可用

- 现象：命令不存在。
- 影响：如果后续要抓取在线文档，需要先安装再接入。

## 5. Fact evidence 不能只靠语义相近兜底

- 现象：早期只做 fact-aware rerank 时，事实展示会被“语义相近的代码块”污染。
- 影响：用户看到的不是最可信的证据链。
- 当前处理：`Fact Evidence` 已切到显式 evidence ref 优先。

## 6. stdio MCP 不能用“每行一个 JSON”糊弄过去

- 现象：标准 MCP 客户端要求 `Content-Length` framing，而不是逐行 JSON。
- 影响：如果只按换行读写，很多宿主会直接握手失败或阻塞。
- 当前处理：`mcp.rs` 已切到标准 framing，并补了回归测试。

## 7. `cargo test` 通过不代表 `colmem-cli.exe` 一定是新的

- 现象：`cargo test` 通过，但 `target/debug/colmem-cli.exe` 的时间戳可能早于最新源码。
- 影响：如果直接拿旧二进制做验证，会误以为“运行面也验证过了”。
- 当前处理：`scripts/verify.ps1` 会优先做逻辑验证，并把 fresh binary 刷新问题单独标记。

## 8. PowerShell 不会自动把原生命令的非零退出码当成异常

- 现象：脚本里直接调用 `cargo test`，即使退出码非零，PowerShell 也可能继续执行后续语句。
- 影响：会出现“验证脚本打印完成，但 cargo 实际失败”的假阳性。
- 当前处理：`scripts/verify.ps1` 统一走显式的 `$LASTEXITCODE` 检查。

## 9. 某些看起来更稳的 Cargo 环境变量在这台机器上反而更糟

- 现象：`CARGO_INCREMENTAL=0`、`CARGO_BUILD_JOBS=1`，以及隔离 `CARGO_TARGET_DIR` 的做法，在当前 Windows 环境里更容易触发 `os error 5`。
- 影响：这些参数不能被当成默认的验证硬化方案。
- 当前处理：默认验证路径回到普通 `cargo test`，fresh binary 验证保留为独立阻塞项。

## 10. PowerShell 写入含非 ASCII 字面量的源码时，必须强制 UTF-8

- 现象：这轮修改 `ingest.rs` 时，PowerShell 默认写入路径一度把 Rust 源码写成了非法 UTF-8。
- 影响：Rust 编译器会直接拒绝读取源码文件。
- 当前处理：后续如果必须用 PowerShell 重写源码文件，统一显式指定 `-Encoding utf8`，并尽量避免把非 ASCII 路径字面量直接写进源码。

## 11. 这个会话里的 Rust 验证有时需要越过沙箱权限

- 现象：同样的 `cargo test` 在当前会话沙箱内会报拒绝访问，但在提升权限后可以完整通过。
- 影响：如果只看沙箱内结果，会把环境权限问题误判成代码问题。
- 当前处理：把“提升权限后的 `cargo test` / `verify.ps1` 结果”作为本轮真实验证结论，同时继续追踪 live binary 的 Windows 文件锁问题。

## 12. 超时的 `cargo test` 可能留下继续持锁的残留进程

- 现象：一次 `cargo test` 超时后，后台仍可能残留 `cargo` / `rustc` 进程。
- 影响：后续验证会继续卡住或触发 `os error 5`，即使源码本身没有问题。
- 当前处理：先用 `Get-Process` 确认残留进程；必要时终止这批验证进程后再重跑 `cargo test` 和 `scripts/verify.ps1`。

## 13. JSON 输出里的 Windows 路径会转义反斜杠

- 现象：`host install` 的 JSON 输出会把 `D:\path` 序列化成 `D:\\path`。
- 影响：测试如果直接匹配 `Path::display()` 的原始 Windows 路径，会产生假失败。
- 当前处理：断言 JSON 输出时先按 JSON 字符串规则转义路径，或匹配更稳定的字段和值。

## 14. in-process smoke 通过后，sandbox verify 仍可能被 Windows target 锁干扰

- 现象：`cargo test` 已通过，但紧接着在 sandbox 里跑 `scripts/verify.ps1` 仍可能因为 `target/debug/deps/*.rlib` 或 incremental cache 删除失败报 `os error 5`。
- 影响：这类失败不能直接等价为 host smoke 或 MCP handler 回归。
- 当前处理：先记录 sandbox 失败，再用提升权限重跑 `scripts/verify.ps1`；本轮提升权限验证通过。

## 15. mcp-router 启动超时过长会拖慢或卡住代理审查

- 现象：通过 mcp-router 间接调用的服务如果启动超时设置过长，子代理审查等待会显著变慢。
- 影响：Architect / verifier 类短审查任务可能被外部 MCP 启动等待拖住。
- 当前处理：已将 `C:\Users\ColaPig\.codex\config.toml` 中 `[mcp_servers.mcp_router] startup_timeout_sec` 从 `120.0` 调短为 `15`。
